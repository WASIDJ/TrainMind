## 三、决策与取舍

## 四、三个关键发现（都是事故，不是设计）

1. **教练一整天是哑的**：`start-7b3.sh` 里早就配好 TTS + LLM + `TRAINMIND_NARRATION=1`，但我一直用裸 `node src/server.ts --mobile` 启动，**整份配置被绕过**。所以之前听到的"沉默"全是故障。
2. **TTS 供应商返回 302**：`ai-maas.../audio/speech` 不直出音频，而是 302 到阿里云 OSS 预签名地址。原代码 `redirect:"error"` 必然失败；跟随 POST 跳转会 405。必须 `redirect:"manual"` → 读 Location → 单独 GET（不带鉴权）。
3. **Firefox Android 没有 `speechSynthesis`**：所以本地 TTS 回退也不可用，手机端**必须**依赖网络 TTS。

## 五、力竭识别调研（结论）

owner 的直觉正确：现在就是按 RMS（约等于分贝）判断，健身房底噪会让它失效。

| 方案 | 组内精度 | 成本 | 结论 |
|---|---|---|---|
| 杠铃速度（VBT，线性传感器） | 最高（行业金标准：组内速度衰减≈接近力竭） | 需贴杠硬件 | 居家自重用不上 |
| **手机 IMU**（加速度峰值计次 + 节奏/幅度衰减） | 中高 | **零** | **首选**，顺带解决"不报数后不知道做了几次" |
| 摄像头姿态（关节角/ROM/速度） | 高 | 需固定机位 + 隐私 | 后期 opt-in |
| 手表心率 | 低（滞后 30-60s，测不了组内） | 需硬件 | 只适合"整场强度/恢复" |
| 麦克风 | 低（嘈杂环境） | 零 | 降级为辅助 |

已做的三层降级：基线改**中位数**（抗突发）、`noisy` 标记（底噪高则降级）、默认静默。

## 八、传感器路线被 owner 否决（同日下午）

owner 明确否掉三条硬件路：
1. **手机**：训练时手里拿着杠铃/哑铃，不可能再拿手机（"训练拿手机肯定不科学"）
2. **杠铃速度传感器**：追问成本，判定不现实
3. **摄像头**：不想架

**由此得出的方向（待 owner 确认后入 D18）**：不做"推断力竭"，改做"**倾听**"——
- 组内麦克风本来就常开，用户会说"停 / 不行了 / 轻一点 / 等一下"
- 这不是"我们问他"，是**他自己开口**，不违反 D17
- 命令词识别走本地 whisper（已有链路），不需要新硬件
- 感知（能量包络）降级为"在家场景的软信号 + 数据采集"，健身房不作为触发器

**技术约束（重要）**：网页端**读不到手表数据**。要接手表必须做原生壳（Android Health Connect / iOS HealthKit / 各家 SDK），并决定是否值得。

**成本量级（需核实）**：专业线性传感器（GymAware 一类）四位数美元；消费级 IMU 传感器几百美元；手环几十到几百美元但需 SDK 支持。

## 九、喊停三段式（owner 补充：一累就歇不叫健身）

owner 原话："用户提出一个是得追问原因的，一累就休息叫啥健身？"

**因此不采用"听到停就停"**，改成教练该有的行为：

| 输入 | 反应 |
|---|---|
| 疼痛词（疼/痛/晕/胸闷/喘不上气…） | **立刻停**，不追问；走安全通道 |
| 疲惫词（累/不行了/撑不住/停…）第 1 次 | **问原因 + 推一把**："是累，还是哪儿不对劲？能顶就再顶一下。"（不答应休息） |
| 疲惫词第 2 次 | 收工："行，放下，歇一会儿。" → `pause` |
| 跳过/换动作/结束 | 直接执行（不属于"退让"） |

实现：
- `classifyStopIntent()` 三分类（含否定词防御：「不疼」「不累」不误判）
- `CoachState.stopProbes`：每组清零，最多追问一次
- 服务端 `coach_message` 分支优先于常规解析

测试：`test/health.test.ts` 新增 2 项（分类 + 两次喊停的服务端行为）。当前 **251 项 / 250 过 / 0 败**。
