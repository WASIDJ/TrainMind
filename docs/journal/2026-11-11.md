**看完的结论与我的预想不同**：后端能力很扎实，问题不在"功能没做"，而在"一眼假"。最能说明问题的三张图：

1. 做「鸟狗式」时，整屏背景是一张**哑铃硬拉**的照片，图上还标着"语音陪练与动作要点"。

**改法上我走了两次弯路**，都记在 fixes/README 里：

- 社区那个"分享此刻"胶囊压住正文。我先加 `padding-bottom` —— 没用，`fixed` 元素盖住什么与留白无关。改成右下角圆点 —— 更糟，压住了"+ 关注"。最后才承认：卡片几乎占满整宽，"悬浮在内容上"这个前提本身不成立，应该移出内容区。

**教训**：调版式不要靠猜，把 `getBoundingClientRect` 和 `position` 打出来，比改十次 CSS 都快。另外，候选方案要"证伪"而不是"试到能看" —— 圆点那个方案如果我没截图，就会以为修好了。

## 动作照片映射纠错 + 计划页封面改版

用户发来一张截图，问"这个输入框很丑"。我先按截图去改输入框，改完重新截当前线上版本，发现**新版输入条早就上去了**（圆角胶囊 + 麦克风图标 + 圆形发送键），用户那张截图是旧的。也就是说这次反馈我一开始接错了对象——真正的线索是截图里顺带露出的计划页。

于是我去截计划页，一打开就看到了：整页铺满一个陌生男人在做绳索弯举。本场根本没这个动作，而照片里的人也不是教练林澄。第一反应是"下载串了"，我去比对 md5，结果 `public/media/freedb/hip-hinge-0.jpg` 和上游 `Good_Morning/0.jpg` **完全一致**——不是下载环节的错，是映射表本身写错了。

`"hip-hinge": "Good_Morning"`：Good Morning 是杠铃负重早安式，肩后架杠铃。我们的 hip-hinge 是自重徒手动作。名字里有 hinge 就映射过去，这是我的错。

`"chair-squat": "Chair_Squat"` 更隐蔽——**名字完全一样**，很容易当作"就是它"。但上游那条的 instructions 第一句是 "first set the bar to a position that best matches your height"，`equipment` 是 `machine`，照片是 Smith 机负重蹲。我们的 chair-squat 是"缓慢坐向椅面后站起"。同名不等于同动作。

所以这次没有去找"更好的替换"，直接删掉了这两条映射。仓库在最初定这个工具时就写死了口径：宁可没有图，也不要拿相似但不同的动作冒充。找不到形态一致的就不映射，走文字版式——这比放一张错的图诚实。

顺带把计划页封面版式也改了。封面拿"第一个动作的照片"铺满整屏，这个设计本身就是错的：封面应该回答"今天练什么"，而一张动作静帧回答的是"这个动作长什么样"。改成封面只放标题和数字，照片只出现在它自己那一行的小图上。

验证：`npm test` 377/376/1/0；freedb-map.json 逐条校验 0 缺失；计划页重截确认。

**教训**：按名字映射外部数据是不可靠的，必须**看图**。我上一轮已经拼了联系表逐张核对，却只核对了 16 张、漏掉了这两张——因为这两张的名字"看起来对得上"，先入为主地跳过了。核对要一视同仁，尤其是名字对得上的那些。

## 训练屏五屏重做

档案页和课程页之后，剩下的是真正的主场——训练时盯着看的那几屏。五屏原来的写法一模一样：每块 absolute 钉在一个位置。

组内屏还算能用，只是"第 1 组 / 共 1 组"和环里的"08 本组目标·8次"在说同一件事，删掉一处。暂停屏中间空三百像素，标题钉在上、语音工具钉在中间、两份进度卡叠在底部。休息屏最糟：倒计时被教练卡压住，"组间休息"和"已完成 1/1 组"两行字叠在一起，中间的空白既不服务阅读也不服务操作。热身屏和完成屏是同一类问题——信息量最少的两屏，反而做了最重的版式。

统一改成竖排流式之后，问题不再是"哪里空"而是"哪块该大"。每条屏只想清楚一件事：这一屏用户在看什么。组内屏看次数，休息屏看倒计时，热身屏看秒数，完成屏看"我做到了"。其它都可以小。

三个顺带修掉的真 bug 里，最花时间的是那个灰色秒数。截图里数字是灰的，鼠标点上去 computed color 却是纯白，opacity 1、没有 filter、没有 mix-blend、没有动画、没有遮挡元素。查了七八轮才想到一招：把颜色强行改成纯红再截一张——红色也变暗了。那就不是颜色算错了，是上面有一层半透明的东西压着。顺着这条线找到 `.visual-text-first::before` 那条四角压暗的渐变，它 `inset:0`、z-index auto，正好盖在文字上。

**教训**：截图发灰不等于颜色算错。先做"改纯红/纯绿还灰不灰"这一个实验，就能把"颜色问题"和"遮罩问题"分开——比逐个 dump computed property 快得多。

另一个教训是被 `.workout-console { display:contents }` 坑了一次，又被 `.tm-ring` 的 `bottom:224px` 继承症坑了一次（改成 relative 之后它被往上顶 224px，环里的 svg 还因为 `inset:0` 撑成了整屏巨环）。absolute 改流式，凡是"位置从别处继承"的元素都要显式归零。

验证：`npm test` 377/376/1/0；五屏 + 320×568 全部实截看过，横向溢出只剩首页建议气泡的横向滑动条（预期）。

## 社区页：先说清楚这一页该多热闹

社区页的问题和前面几屏不太一样。它不缺功能，缺的是**一次减法**：大标题、加入社区的大卡、三个大 tab、五个筛选药丸、分享按钮，每一块单独看都合理，叠在一起就是把内容挤到 446px 以下。把页头收成一行、横幅压成一行、分享按钮并到标题右边之后，第一张帖子回到了 314px。

但真正需要讨论的不是这 130px。用户之前说过"社区很重要，可以先不实现但要讨论"。我这一轮只做了版面，没动内容策略，因为内容策略取决于一个问题：**概念片里的社区，是"已经有朋友在陪"，还是"未来会是这样的"？**

如果是前者，这一页现在这样是错的——真实但冷清，打开就是两三条帖子，观感是"没人用"。如果是后者，现在这样反而是对的：诚实、不造假数据，只是需要一句话把愿景说清楚。

我倾向于后者，因为我们定过一条铁律：不混三态、不宣称没发生的事。造假数据来撑热闹，正是这条铁律要挡的东西。但这是产品判断，得用户点头。
