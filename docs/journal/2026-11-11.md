**审查中最值得记的三条**：

1. **"说一套做一套"比缺功能更危险**。酸痛过滤在"候选不足 3 个"时会整体放弃（这是为了"宁可少避一点也不能排不出课"的合理设计），但 `safetyNotes` 无条件写"今天会控制相关部位的强度"。于是用户说"腿很酸，想练下肢"，拿到的是深蹲+箭步蹲+臀桥，还附一句"已控制强度"。这不是文案问题——它让人以为系统处理过了。

2. **规则方向被写反了**。24h 硬线与周频次针对的都是"同一部位再做高强度"，但账本把所有组一视同仁：一组快走（计时、attentionLevel=low）也会更新 `lastStrength` 那种语义的"上次训练时间"，于是"昨天走了 20 分钟 → 今天不许练腿"。第 23 节自己写的是"只拦力量动作"，实现却是低强度把高强度拦了。修法是加 `buildLightExerciseIds()`，让低强度组照记训练量、但不进频次与间隔判定——**不删事实，只改它参与哪个判断**。

3. **"开-结束"能刷满课程**。`finalize` 对所有终态都调 `recordCompletion`，而 abort 也是终态。实测连点三次"开课→结束"→ 3/12，`measuredSets: 0`。这与 PROGRESS 里"完成的是这一场模板，证据是真实的组记录"直接矛盾。改成 `evidenceSets > 0` 才算，并且**不回退已记过的场次**（否则修完会让演示课程的 6/12 掉回 0）。

**审计自己时的一条**：`set_records` 双写（JSON 行 + v2 行）2026-11-09 已经因为同一个坑踩过一次（那次是删除漏行），但**读路径**至今只走 `json_extract($.sessionId)`，结构性漏掉 60/136 条 v2 行。这次没动它——要统一读数得先决定 v1/v2 谁是事实来源，属于独立一轮，不是顺手能改的。记进未决，不假装修了。

## 界面实测 → 修复第一批（用户：要能宣发见客户）

用户说"完成度和美观性都不足以支撑宣发"。这句话我没法用跑测试来回答，所以先做了一件事：**用无头 Chrome 把产品真正打开，逐屏截图**。演示账号 + 全新空账号，390 与 320 两种视口，一共看了 10+ 屏。

**看完的结论与我的预想不同**：后端能力很扎实，问题不在"功能没做"，而在"一眼假"。最能说明问题的三张图：

1. 做「鸟狗式」时，整屏背景是一张**哑铃硬拉**的照片，图上还标着"语音陪练与动作要点"。
2. 计划页 3 个不同动作（鸟狗式/髋铰链/提踵）共用同一张缩略图 —— 因为 `visualImage()` 认不出就用教练封面照兜底。
3. 记录页 7 场全是「1 动作 · 100%」—— 因为种子脚本的注释写着"演示只留第一个动作(3 组)，保证结组后能干净收尾"。

第 3 条让我意识到：**演示数据的偷懒会直接变成产品的假**。客户不会去查数据库，他看到七场"1 动作"就知道这不是真训练。

**改法上我走了两次弯路**，都记在 fixes/README 里：

- 社区那个"分享此刻"胶囊压住正文。我先加 `padding-bottom` —— 没用，`fixed` 元素盖住什么与留白无关。改成右下角圆点 —— 更糟，压住了"+ 关注"。最后才承认：卡片几乎占满整宽，"悬浮在内容上"这个前提本身不成立，应该移出内容区。
- 训练屏撤掉照片后，我先试"内容竖直居中"，结果是上下都空、更像没做完。用 CDP 打印每个子元素的 `top/height/position` 才看清：底部操作托盘是 `absolute`，根本不参与 flex。改成固定顶距 + 底部安全区才稳。

**教训**：调版式不要靠猜，把 `getBoundingClientRect` 和 `position` 打出来，比改十次 CSS 都快。另外，候选方案要"证伪"而不是"试到能看" —— 圆点那个方案如果我没截图，就会以为修好了。
