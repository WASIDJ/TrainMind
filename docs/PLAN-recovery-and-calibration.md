# 方案：恢复度百分比 + 校准组（2026-11-10）

> 背景：读 Fitbod 算法说明后确认差距——它有「肌群 0–100% 恢复度」和「Max Effort Day（力竭校准组）」，
> 我们只有状态标签和粗粒度反馈。这两项提升"它越来越懂你"的可感知度。
> **本文只是方案，未实现。**

## 一、为什么不能一步到位

两项都会动 `core.ts`（剂量层 + 选动作层）。今天的记录：改选动作的全局权重曾一次性打红 20+ 条断言
（剂量演进、agency 三选一、器械递增全受影响）。所以按"先规则后接线"的顺序分两步，每步都带反向验收。

## 二、恢复度百分比（改动小、风险低）

**现状**：`src/muscles.ts` 输出 `state`（just_trained / recovering / recovered / neglected / no_record）+ 恢复窗口小时数。

**改法**：
1. 新增 `recoveryPercent: number`（0–100）：`clamp(round(100 * hoursSince / recoveryHours), 0, 100)`；
   无记录 = `null`（不假装 0%）。
2. `state` 改为**派生值**（百分比 ≥100 → recovered；50–99 → recovering；<50 → just_trained），
   保持现有调用方不用改。
3. 被落下（≥14 天）仍单独标记，不并入 100%——"很久没练"和"刚恢复好"是两件事。

**接线**：日报表格加一列「恢复度」；记录页肌群列表把文字换成 `恢复中 62%`。
**不做**：手动改疲劳（Fitbod 的 Body tab）、外部活动接入（Apple Health 等）。

**验收**：
- 单测：边界（0h→0%、窗口一半→50%、超窗→100%、无记录→null）
- 反向验收：`state` 派生后与旧逻辑结果一致（用现有 8 项测试当回归网）

## 三、校准组（价值大、风险中）

**要解决什么**：现在的剂量推进只有「轻/刚好/吃力」三档，信号太粗，能力区间收敛慢。
校准组用一个高信噪比样本（这一组到底能做几个）直接校准。

**规则（全部在规则层，LLM 不参与）**：
- 触发条件：该动作有 ≥2 次历史；距离上次校准 ≥6 场；且本次是该动作的**最后一组**
- 表现：该组 `targetReps` 上限 +2，并标 `calibration: true`
- 记录：用户做完报数 → 走现有 `actualReps + actualRepsSource:"counted"|"reported"`，**不新增来源态**
- 校准效果：仅更新该动作能力区间的上界（实测最大次数 ±1），**不直接改下次负重**
- 用户可以不做：跳过不影响任何状态；疼痛照旧走安全门（校准不豁免）

**不做**：1RM 估算（我们没记实际负重为主）、RPE/RIR 交互（已有 targetRir 但不外露）。

**验收**：
- 单测：触发频率（6 场一次）、末组才触发、无历史不触发
- 反向验收（关键）：**接上之后，非校准组的剂量结论必须与今天完全一致**（拿现有剂量测试当对照组）
- 疼痛路径回归：校准组里报疼 → 仍然停止 + 标 pain

## 四、顺序与工作量

| 步 | 内容 | 估价 | 风险 |
|---|---|---|---|
| 1 | 恢复度百分比 + 日报/记录页接线 | 半天 | 低 |
| 2 | 校准组规则 + 测试 | 半天～1 天 | 中（动剂量层） |
| 3 | （可选）肌群恢复度可视化升级为体图配色 | 半天 | 低 |

## 五、我建议的执行方式

先做第 1 步并单独提交（低风险、立刻可见），确认没问题再做第 2 步。
如果第 2 步打红了剂量测试，**回退并先写对照组测试**，而不是改断言——今天已经在"改断言 vs 改代码"上踩过一次。
